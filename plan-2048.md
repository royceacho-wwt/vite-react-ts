# Plan: 2048 Game

## Architecture Overview

A single new page (`Game2048Page`) owns all game state via a custom `use2048` hook.
All board logic lives in pure, independently-testable functions. The component layer is
purely presentational — it renders state and dispatches moves.

```
src/
  hooks/
    use2048.ts              # all game state + pure logic functions
    use2048.test.ts         # unit tests for pure logic
  pages/
    Game2048Page.tsx        # page component + sub-components
    Game2048Page.css        # scoped styles (tile colours, board layout)
    Game2048Page.test.tsx   # Vitest + Testing Library integration tests
```

No new shared components. `use2048` is the only new hook.

---

## Key Technical Decisions

| Decision | Choice | Rationale |
|---|---|---|
| State location | `use2048` hook (local to page) | No cross-page state needed; mirrors WordGame pattern |
| Board representation | `number[][]` — 4×4 (flat `number[16]` also acceptable internally) | Simple to index, easy to clone |
| Random tile spawn | Accepts optional `rand: () => number` (defaults to `Math.random`) | Enables deterministic testing without mocking globals |
| Tile colours | CSS class per value (`.tile-2`, `.tile-4`, … `.tile-2048`, `.tile-super`) | Hardcoded palette; avoids runtime style injection |
| Routing | New `case '/2048'` in `App.tsx` switch | Matches existing pattern exactly |
| Theme integration | Empty-cell colour via `--color-tile-empty` CSS variable in page CSS | Consistent with existing dark/light theming |

## Data Shapes

```ts
type Board = number[][]; // 4×4; 0 represents an empty cell

type GameStatus = 'playing' | 'won' | 'lost';

interface GameState {
  board: Board;
  score: number;
  status: GameStatus;
}

type Direction = 'left' | 'right' | 'up' | 'down';
```

---

## Pure Logic Functions (all exported from `use2048.ts` for testing)

### `slideRow(row: number[]): { row: number[]; score: number }`
Core algorithm. Takes a length-4 array representing one row (or transposed column),
always slides **left**. Returns the new row and the score delta from merges.

Algorithm (left direction):
1. Filter out all zeros → compact array of non-zero tiles
2. Walk left-to-right through compact array; if `compact[i] === compact[i+1]`, merge: set
   `compact[i] *= 2`, delete `compact[i+1]`, add merged value to score delta, advance `i`
   by 2 (skip merged tile — **merge-once guarantee**)
3. Pad right with zeros to length 4
4. Return `{ row, score }`

Right / Up / Down are implemented by reversing or transposing the board before calling
`slideRow`, then un-reversing / un-transposing after.

### `applyMove(board: Board, direction: Direction): { board: Board; score: number; changed: boolean }`
Applies `slideRow` to every row (or transposed column). Returns the new board, total score
delta, and whether any cell changed. Uses structural comparison of before/after to set
`changed`.

### `spawnTile(board: Board, rand?: () => number): Board`
Finds all empty cells (value 0). Picks one at random via `rand()`. Sets it to 2 (if
`rand() < 0.9`) or 4 (otherwise). Returns the new board. Throws (or returns unchanged) if
no empty cells exist — callers must guard.

### `isLost(board: Board): boolean`
Returns `true` if: no empty cells exist **and** no two horizontally or vertically adjacent
cells share the same non-zero value.

### `hasWon(board: Board): boolean`
Returns `true` if any cell contains 2048.

---

## Move Dispatch Order

This ordering is critical. Deviating from it silently produces wrong win/loss behaviour:

1. Call `applyMove(board, direction)` → `{ newBoard, scoreDelta, changed }`
2. If `!changed`: return early — no state update, no spawn
3. If `hasWon(newBoard)`: set `status = 'won'`, update board and score — **stop here, do
   not spawn**
4. Call `spawnTile(newBoard)` → board with new tile
5. If `isLost(boardAfterSpawn)`: set `status = 'lost'`
6. Update state: `{ board: boardAfterSpawn, score: score + scoreDelta, status }`

**Why win is checked before spawn**: avoids a race where a spawn could theoretically fill
the board and trigger a false loss on the same move that won.

## Component Breakdown

### `Game2048Page`
Top-level page. Consumes `use2048`. Attaches `keydown` event listener for arrow keys
(only when `status === 'playing'`). Renders:
- Page heading ("2048")
- Score display (`<span aria-label="Score: N">Score: N</span>`)
- `<Board>` — the 4×4 grid
- `<StatusMessage>` — win/loss overlay (hidden while `status === 'playing'`)
- "New Game" `<button>`

### `Board`
Receives `board: Board` as prop. Renders a CSS Grid (4×4). Renders 16 `<Cell>` elements.

### `Cell`
Receives `value: number`. Renders value (or empty). Applies `.tile-{value}` class (or
`.tile-empty` when `value === 0`). `aria-label="N"` or `aria-label="empty"`.

### `StatusMessage`
Receives `status: GameStatus`. Renders nothing when `playing`. Shows win copy
("You win! 🏆") or loss copy ("Game over! 😢"). Has `role="status"` and
`aria-live="polite"`.

## Test Plan

### `use2048.test.ts` — pure logic unit tests
All tests pass a fixed `rand` function for determinism.

| Test | What it verifies |
|---|---|
| `slideRow([2,0,0,2])` | Returns `[4,0,0,0]`, score delta 4 |
| `slideRow([2,2,2,2])` | Returns `[4,4,0,0]`, score delta 8 |
| `slideRow([2,2,4,0])` | Returns `[4,4,0,0]`, score delta 4 — merged 4 does not re-merge |
| `slideRow([0,0,2,2])` | Returns `[4,0,0,0]`, score delta 4 |
| `slideRow([2,4,2,4])` | Returns `[2,4,2,4]`, score delta 0 — no merge |
| `slideRow([0,0,0,0])` | Returns `[0,0,0,0]`, score delta 0 |
| `applyMove` right | Mirrors left by reversing each row |
| `applyMove` up/down | Transposes board, applies left/right, un-transposes |
| `applyMove` no change | `changed = false` when board is unaffected |
| `spawnTile` | Places a tile in an empty cell; value is 2 or 4 |
| `hasWon` | True iff any cell === 2048 |
| `isLost` full board + no adjacent pairs | Returns `true` |
| `isLost` full board + one adjacent pair | Returns `false` |
| Score accumulation | Two merges in one move both add to score |

### `Game2048Page.test.tsx` — component / integration tests
Use known board injection: expose a `_testInitialBoard` prop (or override `use2048` via
vi.mock) to seed a specific board state for win/loss/score assertions.

| Test | What it verifies |
|---|---|
| Initial render | 2 tiles present, score = 0 |
| Arrow key → board updates | Fires keydown, asserts cell values change |
| Score display updates | After a merge move, displayed score increases |
| Win overlay | Board seeded with one cell = 1024 adjacent to another 1024; fire ArrowLeft; assert win message |
| Loss overlay | Board seeded with no moves remaining; after spawning final tile, assert loss message |
| No move on no-change | Board with a single tile in corner; pressing into wall does not spawn |
| New Game button | Resets board to 2 tiles, score to 0, clears win/loss message |
| Arrow keys ignored after win | Fire ArrowLeft after win; board does not change |
| Arrow keys ignored after loss | Fire ArrowLeft after loss; board does not change |
| Accessibility | Board has aria-label; cells have aria-label; status has role="status" |

## Known Risks & Open Questions

1. **Transpose correctness for Up/Down**: transposing a 4×4 matrix and then un-transposing
   is a well-known source of off-by-one and row/column swap bugs. The unit tests for
   `applyMove` in the Up and Down directions must use asymmetric boards (non-square
   arrangements) to catch swapped axes.

2. **`changed` detection**: comparing `Board` objects by reference will always return
   `changed = true`. Comparison must be value-based (cell-by-cell). A structural equality
   helper or JSON serialisation comparison must be used.

3. **Spawn after win**: the move dispatch order (win check before spawn) is non-obvious.
   A test must explicitly verify that when a winning merge occurs, no extra tile is spawned
   (board tile count does not increase beyond the merge result).

4. **keydown listener lifecycle**: the `keydown` listener must be removed on component
   unmount and when `status !== 'playing'`. Failure to do so leaks listeners and allows
   moves after game-over. Use `useEffect` cleanup or conditional guard inside the handler.

5. **`App.tsx` import sort**: adding a new page import must respect `eslint-plugin-simple-import-sort` order (alphabetical within group). `Game2048Page` sorts before `HomePage`; the import must be placed accordingly or lint will fail CI.
